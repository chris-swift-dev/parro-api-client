# Plan 4: a README that shows what the project does

*Status: done (2026-11-05), merged with PR #4. What differs from the plan: see §6.*

**Goal:** a visitor understands within one screen what this is, sees what it looks like, and knows
how to start. Today the README is 435 lines of text; the first visual is a code block 40 lines down,
and reference material (login internals, three live-check tables) sits between the usage sections.

---

## 1. Principles

- **Only invented data in any visual.** Every terminal image comes from the fixtures in
  `tests/fixtures/` (the De Linde school, Sanne, Mila and Daan), never from a real account. The
  Swagger UI image shows documentation only, never a "Try it out" response.
- **Generated, not hand-made.** A script makes the images, and a test fails when they no longer
  match the code (like the snapshot files). Then they do not go stale after the next release.
- **Text-based where possible.** SVG for terminal output (sharp, small, searchable, diffable),
  Mermaid for diagrams (GitHub draws it). Only the Swagger screenshot is a PNG.
- **Light and dark.** GitHub's `<picture>` with `prefers-color-scheme` shows the right variant.
- **Accessible:** every image has alt text that says what it shows.

still SVG of the overview says the same.

## 3. Other suggestions

1. **A clearer top section:** one-line pitch, badges, the overview image, then a **Quick start**
   in three steps (download a release, `login --prompt`, `overview`). Today the start
   instructions are in prose under a table.
2. **Badges:** CI status, latest release, Python 3.10+, licence (MIT code / CC BY spec),
   "read-only". Shields.io images, no tracking script.
3. **Move reference material out of the README** into `docs/` (linked from a short "More"
   section): `docs/LOGIN.md` (login methods, latch, loopback explanation), `docs/API-NOTES.md`
   (API facts), `docs/LIVE-CHECKS.md` (the three live-check tables), the HAR note. Estimated
   README length: about 200 lines instead of 435.
4. **A short FAQ:** "Is this official?" (no), "Is my password safe?" (read-only, stored where,
   the latch), "Does it work with Parro Basis?" (yes, except the calendar link possibly), "Will
   it post anything?" (never).
5. **Repository settings (by you, not in code):** About text, website link to Swagger UI, topics
   (`parro`, `mcp`, `openapi`, `cli`, `python`), and a social preview image (1280×640, the
   overview SVG on a plain background) so links shared elsewhere show a card.
6. **The Swagger UI page:** a link back to the repository and the releases at the top of the spec
   description, so visitors who arrive there find the client.
7. **`SECURITY.md`:** how to report a problem privately (the project handles passwords and
   tokens).

## 6. Outcome

- **Phase 1:** three terminal pictures (`overview`, `calendar --details`, `announcements`), light and
  dark, from `tests/snapshots/`; `tests/test_readme_images.py` keeps them current.
- **Phase 2:** the screenshot code is its own file, `tools/swagger_screenshots.py`, called by
  `make_readme_images.py --swagger`. Firefox photographs only the window and too early, so the page
  holds back its load event until Swagger UI has drawn and reports its height for an exact second
  shot. The `/calendar/sync` picture shows the description only (no parameters, no "Try it out").
- **Phase 3:** besides login, API facts and live checks, the configuration table and the
  development section also moved to `docs/` (`CONFIGURATION.md`, `DEVELOPMENT.md`). The README
  kept the full command list, the MCP tools table and the config example, so it is 334 lines rather
  than about 200. The release archives include `docs/LOGIN.md`, `docs/CONFIGURATION.md` and
  `docs/API-NOTES.md`.
- **Phase 5:** on github.com the Mermaid diagram renders, every image loads, and the terminal
  pictures switch to the dark variant in dark mode. Not checked: mobile width. Repository settings
  (About, topics, social preview, private vulnerability reporting) are left to the owner.
